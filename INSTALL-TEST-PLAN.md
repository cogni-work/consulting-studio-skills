# Installation checks, broader qualification, update and recovery

S1.2.2 is **owner-tested and accepted for the documented scope**. This plan helps
users check their own installation and extend coverage when their use requires it.
It does not revoke that acceptance or require a full-catalog campaign before
ordinary use. Current evidence and remaining unknowns are in
[AUDIT.md](AUDIT.md#testing-status-and-limitations).

## Begin with a small useful task

1. Follow [README.md](README.md#download-and-install), using the exact
   `consulting-studio-skills.zip` for the chosen release. Compare its SHA-256 with
   the release checksums. Use the supported upload controls available to the
   authorized user; the repository/source ZIP is not the installer.
2. Record the selected package version/hash and actual workspace, client and model
   privately. Confirm that Consulting Studio and its Setup entry are available.
   A visible entry is one observation; successful use is a separate observation.
3. Ask Setup to run **Installation prüfen**. Agree a small fictional or sanitized
   workflow and expected useful result. Read the actual installed skill root,
   task-required references and applicable saved settings through the current
   supported reader. Record unavailable or truncated sections precisely.
4. Perform the task and compare its output with the agreed goal. Keep facts,
   assumptions, source limits and human choices visible. When saving is part of
   the task, agree the destination and effects, save once through an available
   authorized tool and reopen the exact result to check it.
5. Record the tested scope and result. The person using it decides whether that
   result is useful and accepted for the intended work. Retain private evidence
   outside this public repository; report bugs with fictional reproductions.

An ordinary chat-only task needs no storage setup, Studio App, MCP server or new
connection. Use existing readable settings and project records where appropriate;
missing access does not justify creating duplicates or widening permissions.

## Choose further checks for the actual use

| Intended use | Additional observation to obtain |
| --- | --- |
| A different method or mode | Run its ordinary task, read its governing resources and assess its useful output. The package contains 27 consulting methods / 35 modes; a small test does not cover them all. |
| A different model or client | Repeat the relevant workflow on that actual model/client; the recorded Astra result is not a universal compatibility claim. |
| Colleagues or a team | Check each intended role's actual plugin, resource and data access. Installer or owner visibility alone supplies no colleague result. |
| Returning to saved work | Start a new conversation, provide or resolve the exact saved original and freshly read the applicable settings and work. Assess what was recovered and what remains unavailable. |
| Connected read/write work | Verify the selected connection, permitted scope, exact operation and independent readback. Plugin installation grants no app or data permissions. |
| Update or recovery | Follow the controlled checks below; reinstalling identical bytes or changing a display label is insufficient. |

Independent assessment can strengthen evidence for a wider rollout. Label owner
observations, self-checks and independent review distinctly, and include material
assistance or manual repair when describing an unaided-installation result. No
whole-catalog, team, update/recovery or independent host test is claimed by the
current owner acceptance.

## Controlled update

Keep the previous package, settings, adaptations and human work. Use two actual,
reviewed package versions with different hashes and an identifiable changed
instruction/resource. Do not fabricate a version merely to claim an update test.

With the relevant installation owner's authority, inspect current state, use the
host's supported update control and retain the operation's result. Start a fresh
conversation, read the changed instruction/resource and run the affected workflow.
Verify saved settings and relevant adaptations, recording package upload, visible
version, loaded content and useful behavior as separate observations. A missing
supported route or unread changed resource leaves that part unresolved.

## Recovery

If recovery is needed and supported, restore the retained approved package and
configuration through the actual host route under the installation owner's
authority. In a fresh conversation verify the previous content and affected
behavior. A local Git checkout or ZIP replacement alone proves no host recovery.
Recovery cannot undo issued work, messages, permissions or external effects;
reconcile those separately. Controlled update and recovery remain unverified in
the currently documented tests.

## Gaps and uncertain effects

An unavailable tool or route limits the affected step; continue independent
permitted work. On a denied operation, stop that operation. After a timeout or an
uncertain save, upload or update, inspect current state before a retry and retain
known identities. Do not delete an installation, create a replacement record,
change permissions or add credentials merely to make a check pass. Report the
actual operation, surface and unresolved result.

The instructions above do not grant access to anyone's workspace or authorize
installation, communications, sharing or customer changes. They provide a
practical procedure for a user already entitled to perform the selected task.
