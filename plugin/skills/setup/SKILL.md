# Set up Consulting Studio

Use Setup for the **Make it ours** job. Installation does not run Setup automatically.
Use the user's language and reuse readable choices and specific applicable authority
already supplied for this setup. Follow this guided flow and record its choices in
the designated private installation/settings record. Reuse the existing record;
for a confirmed first-use gap, follow the Settings bootstrap below. Do not add a
second intake, configuration registry or tracker.

## Reuse the packaged methods

Read the existing [firm specialization](../org-specialize/SKILL.md) and its
applicable governing/resources through the supported skill reader or local files.
Use its existing procedure for method/settings proposals and adoption; do not
rewrite common methods. For location work, read its packaged
[Workspace Librarian](../org-specialize/references/source/implementation/skills/workspace-bindings/procedure.md),
[binding contract](../org-specialize/references/source/implementation/workspace-bindings/contract.md)
and [storage/lifecycle guide](../org-specialize/references/source/implementation/runtime/storage-lifecycle.md).
These are retained resources in the same plugin. Apply the shared **Deliverable mode
and home** section of the linked storage/lifecycle guide. Select and read the exact required
sections for the chosen workflow, including narrative-shape, evidence-visualize,
publishing-render and publishing-inspect when applicable. If the current reader or installed version cannot
reach a required resource/section, report that exact gap and stop only dependent work;
do not replace the method with remembered instructions or treat an older retained
resource as proof of the current contract.

## Discover standards before asking for missing choices

Before asking which firm policy, index or design to use, actively search the
relevant permitted firm context and read the applicable candidates with current
tools. Start from the selected context, readable settings/index/catalog and known
references; include firm rules, design/template references and storage conventions.
Do not require the user to supply a link to a reference that this bounded discovery
can resolve. A name or search result is only a candidate: read the original and
retain its observed identity, revision, owner, scope and coverage. Reuse compatible
existing references, including design references; do not recreate or overwrite them.
If the relevant context itself is missing, ask only for its understandable name or
link. No unrelated/global search or new access follows.

Report each relevant topic as found-and-read, confirmed missing in the inspected
scope, not found in a limited search, inaccessible, or not checked. Only adequate
bounded inspection plus a responsible person's confirmation that no other rules
apply establishes a gap for a new standard. A limited search, unreadable reference
or unavailable tool proves no absence. Explain the actual coverage/access gap and
ask one focused question, for example: "Do you already have rules for naming
project documents, perhaps somewhere else?" Reuse an answer already supplied.
Do not repeatedly ask about found rules. Multiple applicable candidates or
conflicts need an owner choice; never guess the governing reference. A required
unread reference blocks its application, not independent permitted preparation.

## Offer small proposals for confirmed gaps

For confirmed gaps, offer a **proposed starting point**, not a firm fact or a list
of mandatory intake fields. Select only what the chosen workflow needs and show
existing rules alongside the few still-open decisions. For example:

| Missing topic | Optional starting point to discuss |
| --- | --- |
| Storage | Reuse suitable authorized homes; reference central designs/templates and keep each engagement's confidential material in its own dedicated Shared home by default. A chat-only route can remain transient. This proposes no new Space, fixed tree or access grant. |
| Naming | Use a short recognizable project reference and document purpose; where supported, add the exact version. Translate an agreed rule only to the finite naming parts supported by the current schema. |
| Versions and status | Keep identifiable revisions and human changes; distinguish draft, reviewed, released and accepted. A save or generated revision does not advance these states automatically. |
| Responsibility | Propose the relevant roles: engagement lead for project work and a firm settings/design owner for shared rules. Ask who will take an unresolved role; invent no person, current owner or approval. |

Ask whether to keep, change or defer the specific proposal; do not make every row a
required question. Missing storage/naming/override rules do not prevent a labelled
read-only proposal in chat or independent ordinary work. Existing design rules can
be reused while unrelated gaps remain open. Do not invent a policy identity,
revision, owner, firm rule or an organization-wide permission for project overrides.
A proposal is not an effective reference. Only an attributable responsible human
decision bound to the exact proposal and scope can legitimate adoption through
org-specialize; saving configuration, provisioning and rights remain separate
supported authorized effects with their required confirmation and readback.
Do not call `propose_workspace_setup` until its required source, policy, target and
revision fields are genuinely resolved; never fill them with suggested facts.
On a repeated Setup run, freshly read existing rules, decisions and prior effects;
reuse them and propose only the remaining gaps. No duplicate standard, settings
record or home, and no silent automatic adoption follows.

## Discover, choose and agree the smallest useful environment

1. Inspect bounded account/workspace and home metadata, available apps, actual
   connections/accounts, configured actions and current-runtime exposure. Inspect
   relevant existing settings/index/catalog, homes and design/template references
   supplied or selected by the consultant. When identities are missing, discover
   candidates only in the relevant permitted context; do not scan unrelated projects
   or private content. Separate observed capability, owner-reported practice and
   unknowns. A declaration, connection, provider name or plan proves no operation.
2. Follow Make it ours in order: relevant workflows/methods and desired output forms;
   existing templates, language/design and quality/approval rules; then necessary
   storage and app actions. Offer inspected provider/account/action choices for the
   consultant to select. Mixed layouts are valid: source, settings, entity and output
   homes can use different supported providers. Reuse adopted versions and compatible
   homes; the five logical areas impose no fixed folder or Space tree. A full firm
   profile is not required for ordinary use. Ask only missing consequential choices.
   If dependent tailoring needs geography, client breadth or service focus, obtain
   those choices or explicit adoption of an exact existing target brief. Historical
   profiles, interface language and examples select no defaults.
   Keep geography, client industry/segment breadth and consulting service/function
   separate in the existing domain brief and installation/settings fields. Missing
   choices stay unknown. Map applicable terminology, evidence dimensions, methods
   and output forms to affected skills, exact references/versions, owners and
   candidate/adopted status through org-specialize. Clarify conflicting choices or
   unread mandatory references only for dependent tailoring; ordinary neutral work
   can continue. A labelled example never adopts its target or requirements.
3. Show **current state, concrete target layout and exact proposed changes** together:
   selected workflow/output types, resource identities/parents, owners, context,
   audience, actions, initial content/references, reuse/create decisions and gaps.
   Keep sources and output destinations separate. Unreadable or denied homes are
   not absent. Reconcile prior effects by actual identity/content before retries or
   resumption; do not create duplicates. The consultant agrees the target and changes
   before provisioning. Existing specific authority can cover the selected effects;
   obtain only missing decisions and actual required action-time confirmations.
4. For each selected workflow/output type, settle chat-only/transient versus retained
   mode. In existing binding/destination/authority fields, record authoritative home,
   owner/audience/context, supported save/update/readback, current authority, effective
   form/content/design references, standing retention scope and configuration revision.
   An entity's authoritative home outranks an unrelated personal preference; a source
   home chooses no output home. An explicit chat-only request overrides standing
   retention. Read-only queries create no unsolicited retained copies. A retention
   choice alone proves no save. A synthetic example supplies no real-client data
   admission, retention authority or production grant.
5. For improvements, discover supported issue trackers and **recommend issue-based
   tracking by default**. Confirm the installation's actual tracker/project/destination,
   owner/triage, audience, permitted material and filing authority; a Page backlog is
   an explicit alternative. Configure the existing `feedback-drafts` role and record
   filing versus review-first preference with its revision in existing settings.
   No forced GitHub dependency or silent fallback. Do not automatically create
   issues/projects or migrate an existing backlog; those need a separate concrete
   supported request and applicable authority. A future useful issue records the
   problem, desired outcome, acceptance criteria and permitted evidence, with a
   linkable lifecycle to later PRs where actually supported. Filing implies no
   adoption, implementation or release.
6. Apply only the agreed supported operations under applicable authority. Reuse
   compatible homes and create only selected supported missing structure. Preserve
   accepted records/settings, wiki content, human notes/dissent, issued work and
   confidential boundaries.
   Home creation, settings adoption and configuration/binding persistence are separate
   effects: save and read back configuration separately from home creation, including
   its effective revision. Use the one designated private checkpoint/updater, or the
   existing explicitly selected owner-retained route. Keep actual installation
   locations, private settings, design assets and resource IDs in that authorized
   configuration home, outside reusable methods. Missing apps/actions,
   connections or grants remain owned gaps; do not expand sharing, connect/install
   apps, handle credentials, send business messages, publish, delete or schedule.

## Bootstrap and recover durable Settings

This is the common rule for the App and Skills-only variants. A private Settings
Page or another observed supported native settings home is sufficient; no dedicated
Studio database is required for this record. Settings storage, an attributable owner
decision, discovery bindings and later-session application are separate facts.

1. **Discover before creating.** Freshly read the selected context's designated
   settings/installation record, relevant index/catalog, supplied direct locator and
   prior setup effects where present. With no known locator, use the Librarian's
   generic `Consulting Studio Start Index` discovery contract first; no specific
   Settings title or ID is needed. Follow bounded discovery above and reuse a
   compatible record. A limited search, missing tool, unreadable record or denied
   access proves no absence. Multiple candidates or conflicting current settings
   require the responsible owner's resolution; do not overwrite or create a parallel
   record. Continue independent permitted work while dependent settings work waits.
2. **Offer a concrete first home.** For an adequately inspected, owner-confirmed
   missing Settings record, actively offer the smallest suitable private Settings
   Page through currently available Pages actions. Inspect the actual target/parent,
   owner, effective audience and supported create/read/update operations first; a
   Page title or nesting proves no privacy. If Pages is unavailable, offer another
   inspected supported native settings route. If none is available, return the exact
   proposed content and owner-mediated save/read steps as an unsaved handoff. Do not
   stop at "settings are not saved" without a concrete next step. Access denial is
   not unavailability: stop the denied action without a replacement or silent fallback.
3. **Confirm the exact settings effect.** Show target/provider/parent, title, scope,
   accountable owner/updater, audience, exact initial content/references, proposed
   status and supported operations together. Include only agreed choices and actual
   observed reference identities/revisions; unresolved fields stay unknown. Keep
   candidate and adopted settings explicit, with the attributable owner decision
   bound to the exact content and scope through org-specialize. Reuse valid specific
   authority, but obtain missing confirmation before writing. Approval of a project
   Page alone does not authorize a Settings write, owner adoption or index creation/edit.
   Prepare one designated record, not another tracker or a copy of client content.
4. **Create once and read independently.** Perform only the confirmed supported
   create/settings operation. Retain returned identity/locator and operation outcome;
   then reopen that exact identity through a separate native read. Compare meaningful
   agreed content, scope, status, owner/audience and actual revision where available.
   Never invent an ID, URL or revision. A create response alone is saved-unverified;
   missing or mismatched readback leaves completion open. A conflict requires a fresh
   read and a newly agreed guarded change preserving human edits/dissent. For an
   unknown create outcome, reconcile the same attempt by returned identity or bounded
   exact-reference inspection before any retry. Unresolved or ambiguous effects
   prohibit another create; absence from search alone does not settle occurrence.
5. **Offer and test the start index and registration.** Explicitly offer the exact registration
   in a suitable existing private index/catalog or supported discoverable native
   settings entry: actual locator/identity, owner, workspace, context, purpose, scope
   and observed revision. Apply the Librarian's generic searchable start-index label
   and contract marker so a fresh chat needs no private title or ID. Reuse an existing
   compatible index/section. If bounded inspection plus owner confirmation establishes
   that no suitable start index exists, concretely offer its smallest private native
   Page/section with that generic label, matching scope/owner/audience and the exact
   Settings reference. Index creation and Settings registration each require covered
   confirmation before their supported writes and separate readback; Settings storage
   alone does not authorize either. This reuses the Personal Index/Shared Catalog
   roles, not a second Settings record or progress tracker.
   Show the exact addition and audience; obtain its specific
   authorization before editing. Preserve existing content and separately read back
   the binding/revision. Home readback is not binding readback. Invoke the packaged
   Librarian's bounded discovery from the intended normal entry without handing it
   a specific index/Settings title or locator; start from the generic contract and
   freshly read and compare the exact record found. If this
   cannot run, record discovery as untested with the precise missing operation.
   With no reliable supported discovery route, offer the actual direct locator as a
   manual fallback for the owner to retain; do not present repeated link entry as the
   normal route. A start index is not a prerequisite for saving Settings; offer it
   to enable reliable discovery, not as a mandatory tree. A direct locator alone
   proves neither discovery nor later-session application. Keep private settings out
   of broader project/navigation audiences.
6. **Report the separate states.** State Settings storage/readback, owner decision
   documented or pending, discovery bindings checked/missing/not checked, and
   later-session application checked or untested. Plan a separate fresh-session
   probe through activated Consulting Studio/Librarian without a supplied Settings
   locator or prior-chat contents. It must discover the registered entry, freshly
   read the record and match acting user, workspace, context, purpose, scope and
   effective rights before applying only applicable adopted settings. Without an
   actual fresh-session observation, later-session application stays untested. A
   foreign context or colleague inherits no choices or grants. No automatic global
   effect, method rewrite or automatic adoption follows; there is no autoload promise
   in arbitrary chats or without the relevant skill/workflow invocation.
   If no durable progress record exists yet, return the observations/locator for the
   owner to retain; do not assume that this handoff has itself been saved.

**App branch:** additionally inspect actual Studio configuration and any selected
project adoption separately through available supported read routes. A Settings
Page neither saves Studio/D1 configuration nor adopts a project. Any missing App
operation blocks only that dependent step; native Settings work can proceed within
its own authority. **Skills-only branch:** no Studio App, MCP, D1 or studio-resume
operation is required or inferred. Use the same native Settings and Librarian
discovery procedure; manual locator recovery is a fallback, not the normal entry.

## Offer an optional workflow check

Offer three choices: **skip the workflow check for now**, **use permitted supplied
content**, or **try a clearly labelled synthetic example**. Reuse an explicit
choice already made for this setup. Skipping does not block normal use or the
agreed supported setup work; record the workflow check as not run, with the
remaining checks visible. Setup imposes no product-wide synthetic-only mode.
Normal projects start empty and use user-provided or authorized content. Never
automatically insert example sources, requests or results into normal projects,
homes, settings or knowledge. An example is neither a firm default nor real evidence.

For an optional synthetic run, offer the small reusable
[optional synthetic example](references/optional-synthetic-example.md) or a
compatible explicitly selected existing test dataset. Read that resource only when
the example route is selected. Agree its bounded request, success criterion and
chat-only or separate clearly labelled test destination before any effects. Keep
the synthetic designation visible in input, request and result lineage, including
on resumption; never relabel a historical fixture as real. Inspect earlier effects
before retrying and prefer a compatible existing test record. No automatic copy,
retained write or live operation follows from reading the resource.

For permitted supplied content, use the selected ordinary workflow under its actual
source, audience, use and retention authority; ask only for missing applicable
authority or policy. Existing valid arrangements can suffice. Synthetic example
success grants no real-client admission or retention acceptance. If material is
not authorized, stop only its dependent work and offer permitted preparation or
the optional synthetic route. Mark any prepared output unaccepted.

If a workflow check is selected, agree one small useful ordinary request and success
criterion in the selected scope. Offer a scoped ordinary presentation workflow when
the consultant selects presentations; a generic test note does not substitute for
that choice. Apply the following checks to the selected workflow only.

For a presentation, reuse its actual audience/purpose, permitted content and effective
design/template references. Apply publishing-render's explicit question: **"Would you
like me to use narrative-shape to shape this for your audience before I produce it?"**
Use the user's language and wait for this request's explicit yes or no before creating,
editing, rendering or exporting. Silence, supplied story or remembered preference is
no answer. Reuse an actual answer on continuation of the same request; a new request
needs its own question. On yes, apply narrative-shape with the consultant: develop
and settle the central message and story arc through their actual feedback before
full production. Reuse an established direction; explicit independent drafting stays
labelled with its delegation and assumptions. On no, preserve the supplied argument,
emphasis, sequence, qualifications and dissent. For a substantive report/presentation workflow, explicitly apply evidence-visualize
before production, validate reusable figures or record a justified text/table-only
outcome, and coordinate with the actual narrative choice. Integrate selected figures
beside their arguments with visible captions/sources/qualifications and static export
fallbacks; inspect every selected final figure in every requested format. Then render
and inspect the exact artifact through the supported route. An unavailable required method blocks dependent
production; do not silently switch routes or call an outline a finished presentation.

For retained output, use the actual agreed output home and present exact proposed
content/destination for any required write confirmation. Save through the supported
operation, then reopen the returned identity through a separate read and compare
meaningful content/revision. Retain actual save/readback receipts. Save/read back
configuration separately when selected; creating an output or home does not establish
configuration persistence. A local draft or create response alone proves no reopening.
For an explicit chat-only/read-only selection, perform no unnecessary retained write;
state retention/save/reopen as not applicable with its reason. If a retained setup
check was required, an unsaved draft cannot pass it.

Return the current/target layout, choices, effective configuration revision, reused
references and, for a selected workflow, exact output home/identity/version/state,
actual operation/readback receipts and result link, plus each gap's owner and smallest
next action. For a skipped check, report no workflow output or save/readback and
keep its status not run; do not invent an output identity or acceptance. State omitted
retrieval, rendering, semantic/visual/reader checks, colleague access and continuity
honestly. Claim discovery, provisioning, readback or workflow success only from
actual observations; obtain the owner's separate acceptance. Keep prepared, saved-unverified, saved-and-reopened,
owner adoption and acceptance separate. A blocked save remains blocked; continue
independent permitted preparation without claiming completion. Use the existing private
installation record, not a parallel tracker. Stop after this agreed onboarding scope;
other workflows, WA adoption and real-client admission need their own applicable checks.
