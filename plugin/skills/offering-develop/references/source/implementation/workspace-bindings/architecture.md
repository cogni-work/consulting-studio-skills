# Workspace location responsibilities

Find the authoritative home for the acting user, context and purpose. Reuse it or
prepare the smallest concretely authorized missing-home change, then maintain
references, ownership and lifecycle handoffs. Read the [binding contract](contract.md),
[skill roles](../runtime/binding-catalog.json) and [storage lifecycle](../runtime/storage-lifecycle.md).
Personal Index and owner-managed Shared Catalog are current private settings in
their selected homes. Use valid mappings directly with current checks; no mandatory
Librarian invocation or whole-workspace scan is needed.

## Components and responsibility

| Component | Responsibility | Authorized home |
| --- | --- | --- |
| Business skill | State question, entity inputs, logical location roles and useful proposed output; preserve its business authority | Exact selected method/settings versions; observe effective installed version separately |
| Personal discovery index | User's relevant search preferences and references to shared catalogs; remembered explicit output selections | Owner-designated personal wiki/settings home outside Git; belongs to user, not agent |
| Shared catalog | Owner-maintained location inventory, permitted purposes/audiences, governing policy references and effective revisions | Particular shared owner's designated configuration home outside Git |
| Resolution step | Combine acting user, selected business context, current entity references, explicit choices and catalog constraints; return exact selected locations or a missing choice/blocker | Current workflow through an actually supported authorized route |
| Provider route | Perform an actually supported operation under current caller access and information-use authority; report version/coverage/effect | Existing authorized connector, native tool or owner-mediated route |
| Wiki entities | Identifiable typed sections/pages, contributions and accepted revisions with dependencies | Actual selected Personal or particular Shared home, outside Git |

Personal and Shared are categories. A firm, team or project is a context label and
identity on a particular Shared home; these labels are neither mutually exclusive
nor an access hierarchy. Projects may use several locations. Client ownership,
retention/exit and information-use restrictions survive the category simplification.
Keep the current authoritative home of each entity; a new output destination does
not move existing facts. Cross-home references must disclose their actual read coverage.

## Resolution and execution

1. Identify the acting user, actual workspace/connection and selected work context
   through the available authorized route. A displayed name or shared agent is
   insufficient identity/access evidence. Missing context can be clarified narrowly;
   an ordinary supplied-material draft requires no full registry setup.
2. Resolve known entity IDs at their current homes. Read the personal index only
   where useful for discovery, following references to relevant authoritative shared
   catalogs. The user can supply a permitted location directly. Do not scan every
   accessible repository, project or catalog to bootstrap missing preferences.
3. Filter relevant candidate research/knowledge sources by question, current user
   access, purpose and applicable restrictions. A preference ranks permitted sources;
   it does not expand the search scope or certify an answer's recency/acceptance.
4. Resolve output roles independently: an explicit request or same-user/context/purpose/role
   remembered selection supplies the proposed destination, then current owner policy
   constrains it. Catalog defaults are proposals until explicitly adopted. Ask only
   for an unresolved choice that changes the work. Conflicts/denial return a blocker;
   do not apply a broader default or silently fall back to another home.
5. For each needed operation, inspect current access, information-use permission,
   readable applicable policy, target audience and actual route capability. Capability
   evidence is scoped to actor/connection/location/configuration, not a universal
   provider feature flag. Source and destination authorization are separate.
6. Prepare the complete contribution and exact source/version/passage dependencies.
   Use supported save/create only within a valid task or standing contribution grant.
   Saving to Shared is a disclosure to its audience. Acceptance stays with the curator.
7. Inspect the resulting exact identity/version and meaningful content through a
   separate readback before claiming verified retained delivery. A successful save
   with a returned identity can establish storage occurrence while content readback
   and user handoff remain incomplete under the [common contract](contract.md).
   Record unresolved effects privately and inspect before retry. A later accepted
   synthesis revision incorporates only evidenced accepted contributions through a
   demonstrated safe update or controlled owner incorporation.

Remembered choices are per user, business context, purpose and logical role;
topic/entity qualifiers distinguish multiple appropriate wikis within that context.
Storage and lookup use the same complete key. Distinct internal-research and
client-facing choices stay separate even when both homes allow both purposes;
an entry without a required key supplies no broader fallback. Store selection,
owner policy revision and attributable choice reference through authorized settings
save/read. Revalidate on use. Changing settings changes future resolution, never wiki
content. A locator change needs an authorized identity-preserving relocation record,
readback and relevant citation rechecks; it is not an automatic migration.

Use the [common contract](contract.md) and [skill roles](../runtime/binding-catalog.json).
Read required instructions through the supported reader in the current environment.
An unread reference blocks only dependent work; continue permitted independent preparation.

## Provider operations and verification

Inspect the tools and schemas actually exposed in the current environment. Treat
search, read, create-contribution, readback, accepted-revision incorporation,
version/passage navigation, conflict protection, export and continuity as separate
capabilities. Use the [provider-operation guide](../skills/workspace-bindings/references/provider-routes.md)
where relevant. A search-only route may support inspected evidence without retention.
When a needed operation is unavailable, return a precise owner-mediated handoff.

Record exact actor, connection, resource, configuration and observed operations.
A successful local save or current-session read proves neither shared-reader access
nor later-session continuity. Check the required audience, independent review and
human acceptance separately. Never infer grants from a catalog, assistant instruction,
provider name, deployed view or installed package.
