# Storage provisioning and lifecycle

Apply this guide when selected work needs retention, shared use, setup, transition
or closure. Use the current designated private instance/installation record if one
exists; preserve choices, mappings, receipts and gaps there. Keep live locations and
private content in authorized homes. Perform only supported authorized operations.

## Deliverable mode and home

Resolve delivery mode and the authoritative output home early, before substantive
work depends on retention. Reuse the current request's explicit choice, the entity's
current home and applicable adopted Setup/workflow preferences. A proposed new
output home does not relocate an existing entity. Ask one focused question only
for a missing, ambiguous or materially changed choice; do not ask again for a valid
standing choice on every ordinary request. A read-only query remains unretained
unless a separate applicable retention instruction is in scope.

For the selected workflow, read its current configuration: requested form/content,
applicable exact template/design references, output mode/home, owner, audience and
material/context limits, supported operations, standing retention or review/filing
preference and configuration revision. Keep these in the existing installation,
settings or entity record, with attributable choices and observed save/readback.
They are not additional location-selector key dimensions and confer no operation
or information-use authority. A synthetic setup check supplies no client-data grant.
Mandatory client form and required readable references retain precedence.

Explicit chat-only/transient delivery produces no retained copy. Say where the
useful answer is delivered without inventing a saved record. Source locations do
not choose the output destination. For retained delivery, verify the current exact
home, principal, outgoing material/audience permission and required save/update/read
capabilities before writing. A standing retention choice can authorize routine
filing only within its evidenced scope; obtain any still-required human decision.
Do not silently substitute another provider or Personal home after denial.

Carry the selected mode, authoritative home, stable identity/exact version,
configuration and actual preparation/save/review state through each skill handoff.
Reuse those choices rather than start destination intake again. Preserve human
originals, dissent, issued versions and one current home per fact. Saving a review
copy does not change its source entity's business state or confer approval.

Complete retained delivery by saving the exact output through the supported
authorized route, reopening it to check identity/version and meaningful content,
and returning its usable final link or precise manual retained-file reference.
Verify intended-reader navigation separately where required. Keep prepared,
saved-unverified, saved-readback and human review/release/acceptance distinct. If
save or readback is missing, report the useful draft and precise incomplete state;
do not claim completion. Reconcile uncertain prior writes by identity/version/content
before retrying; inaccessible or uncertain does not mean absent.

### Library saving and document handoff

Apply this same contract in App-assisted and skills-only chat. Library files,
Studio/D1 work state and Pages are separate routes. Resolve the requested route
and only its necessary destination, material/audience permission and operations.
Use the existing Library skill and currently exposed authorized Library tools;
Studio adds no Library connector, transfer helper or file store. An explicit
permitted Library destination needs no Studio project, Pages tree or complete Setup.
Keep the existing Setup and Workspace Librarian discovery procedure for work that
actually depends on Settings or an unresolved home. Librarian is optional location
help. `check_workspace_readiness` reports Studio configuration, not actual Library
tool availability, access or execution. A missing setup check establishes no cause
for a failed save or handoff.

Keep three observations separate, in the current conversation or existing authorized
record; do not create a tracker merely to collect them:

| Observation | Evidence and honest disposition |
| --- | --- |
| Storage | A successful save operation for the exact selected output with its returned file identity. Preserve the exact returned Library identity, file identity, filename/path and any actually returned version. A local prepared file, URL, tool availability or metadata-helper result alone proves no remote save. Missing or lost acknowledgement leaves the effect unknown, even if a local file exists. |
| Content readback | For the agreed save/reopen test, separately read exactly the returned identity through the supported Library route. Compare meaningful content with the selected output; record read coverage and actual version observations. Metadata, search snippets, echoed create content and the original local file are not independent remote content readback. Truncated or different content is incomplete or mismatched. For byte-level verification use the existing Library skill's supported materialization/comparison route. Never invent a version, immutable link or edit guard. |
| User handoff | Offer the supported document card/file attachment or exact supported document reference for that identity. Preserve its returned target; do not construct a link from an ID. Local paths and private/signed transfer URLs are not a usable document handoff. Verification of the offered reference and actual intended-user opening/download on a named surface are separate observations; an assistant tool read proves neither rendered link display nor user access. |

A successful save may be reported as saved while readback or handoff remains
incomplete. A returned supported reference can be offered with that qualification
before readback; it proves no content check or actual opening. If content is readable
but the document card/link is absent, say that storage and readback are confirmed
and the user handoff is unresolved. Repair or reopen the same identity. A separately
requested supported attachment can provide a handoff; it is no second Library save
and establishes no new authoritative home. Do not claim complete retained delivery
while a required readback or usable handoff is missing.

| Negative observation | Next step within current authority |
| --- | --- |
| Exact identity reports missing | Record the exact missing-file observation and reconcile it with the original save result; do not infer absence from search or automatically recreate. |
| Exact identity is denied | Report blocked access, without claiming the file is missing; no replacement home, access expansion or unchanged denied-read retry. |
| Read tool unavailable or content incomplete/mismatched | Preserve the save receipt and precise verification gap. A successful save remains distinct from current content verification. |
| Save outcome unknown, with or without an identity | Preserve the attempt and returned observations. Read that identity/current operation state where supported; with no resolvable identity, use only bounded authorized reconciliation and leave the outcome unknown if it cannot be settled. Never repeat create or save another copy while an earlier effect is unresolved. A missing/denied read or empty search alone does not settle non-occurrence. |
| Search/list is empty or stale after save | Search indexing/discovery is separate from exact-ID readback. Prefer the returned identity; do not create a duplicate to repair indexing. |

For synthetic contract probes keep the selected output/identity, save observation,
separate read request/response and content coverage, offered handoff target and
surface-specific opening evidence independently attributable. Reject claims beyond
those observations and reject a repeated create after an unknown effect. Local
probes establish no actual provider or model execution. Browser evidence, iPad
browser evidence and native iOS/iPad app evidence are separate; simulation or success
on one surface transfers no pass to another. A Library-only operation binds no
Studio project, writes no D1 result/receipt and changes no Pages or business status.

## When to reuse or create a home

Resolve the agreed storage home **before the selected work depends on durable
retention or colleague reuse**, not automatically whenever someone names a project.
Use Shared for the chosen shared-work context; permitted Personal retention and the
manual retained-file route remain available for their distinct purposes. Inspect the
existing authorized home first. Reuse it when identity, purpose, audience, policy and
operations fit; create only missing authorized homes or sections needed for that work.
Several logical groups may be sections in one home, or one project may need several
homes. Neither document nesting nor a shared agent establishes an access boundary.
A useful supplied-input draft needs no complete wiki or firm-storage setup.

| Trigger | Reuse/create decision and initial content | Accountable owners and authority |
| --- | --- | --- |
| Initial firm installation | Inspect the existing firm catalog, effective methods/settings, knowledge and output homes. Select only the missing resources needed for approved workflows; retain attributable target/adoption and handling/continuity references. A published skill library is separate from firm knowledge storage | Workspace/configuration owner coordinates; information, method, knowledge and maintenance owners retain their own decisions. Whole-workspace method availability does not grant content access |
| Design/brand work or a required firm/client form | Reuse the current authorized design library. If a new candidate/library is needed, select its destination and retain exact specification/assets/template references, revisions, applicability and asset rights; unresolved client-form conflicts stay visible | Firm/client design or method owner settles applicability and adoption under `org-specialize`; candidate, adopted and applied remain distinct. No separate design Space is mandatory |
| Restricted pursuit or standalone work before a delivery authorization | Choose an authorized context before real material admission and a restricted durable home before retention/sharing. Start with relevant Need/Buyer Brief, permitted sources, follow-ups, draft offers and human choices only as needed; keep unselected private notes separate | Relationship/pursuit or named standalone work owner plus information owner. Record purpose, participants and handling/exit basis; storage creates no Opportunity, buyer decision, order or paid-work authority |
| Authorized engagement or transition from pursuit to delivery | Proposed default: reuse the engagement's existing dedicated Shared home or establish one before durable client delivery or colleague reuse. Reference the actual work basis, exact promise/framing, lead/sponsor, permitted participants, effective methods, continuity owner and exit terms; preserve pursuit originals and gaps | Engagement lead and applicable sponsor/contracting, information and storage authorities. A work order/internal decision or separately bounded applicable own-risk authority governs work that may proceed; provisioning does not supply it |
| Changed project, audience, policy or resource needs | Revalidate the current mapping; revise it or propose another home only with the relevant owner's decision. A new project label need not produce a duplicate home; an access failure authorizes no substitute | Current information/configuration owner and affected work owner; proposed access/relocation and changed work have their separate approval and recheck requirements |
| Permitted synthetic check | Reuse a suitable authorized demo home or provision a clearly labeled synthetic home only under the check's concrete storage/action authority. Seed synthetic examples and visible limitations; identify demo audience, owner and planned disposition | Check owner and actual resource/workspace authority. Demo setup establishes no commercial engagement, production configuration or real-client admission |

Unknown homes, unsupported operations or missing authority stay owned gaps under
[selected-workflow requirements](requirements.md#verification).
Return a permitted unretained draft/manual handoff where appropriate; do not silently
create a replacement home or move content from a denied Shared home to Personal.

## Engagement home and access boundary

The proposed default is **one dedicated Shared home per engagement**, with
distinct resource identity, accountable owner, explicitly decided membership/access,
authoritative record assignments and its own retention/closure handoff. Reuse an
already designated compatible engagement home rather than create another. The
installation owner explicitly adopts this choice or records an exception through
the setup conversation; verify the required separation through actual audience/access observations before relying on it.
Several authorized sources or artifact destinations may still serve the engagement;
record each fact's current authoritative home and the precise boundary of each resource.

A SharePoint site or a separate ChatGPT Space is a physical candidate only where
observed capabilities meet that engagement's access, operations, continuity and
retention requirements. A nested folder or sub-space is an evaluated alternative,
not an assumed host feature. Use it as an explicit exception only after the owner
records the reason, actual inherited/explicit access and audience, retention/exit
terms and evidence that the required boundary works. Document hierarchy, a separate
name or an instruction to stay within it proves no isolation. If required controls
are unavailable or unknown, keep the mapping blocked or propose a permitted alternative.

Reference central reusable methods, permitted proof and effective design/template
versions under their existing rights rather than duplicate entire libraries. Keep
client/project adaptations, draft designs and confidential material within their
authorized project boundary, with separate configuration-adoption authority where
applicable. Central references do not expose project content to the central library's
audience, and project membership grants no extra access to central material.

## Starting logical configuration

Use the canonical [five logical information areas](storage-lifecycle.md#five-logical-information-areas)
for purpose, content, accountable roles and authoritative-home/reference assignments:
Marketing, Sales, Delivery, Standards and Persönlich (Personal). Reconcile selected
needs with existing homes and contracts; start with the smallest useful identifiable
sections/references. These areas are not a mandatory folder tree, exactly five Spaces
or a replacement for suitable sites. Do not copy libraries or engagement dossiers to
fill a template. Creation/revision triggers and the [ordinary location examples](storage-lifecycle.md#ordinary-location-examples)
reuse this guide's approval, access and lifecycle gates; verify their actual effects separately.

Keep the existing logical binding roles: `knowledge-wiki`, `research-sources`,
`entity-home`, `method-settings` and `artifact-home` describe the selected operation's
need, not five new catalog categories. Sources, knowledge and artifact destinations
are resolved independently. Accepted knowledge and effective methods/settings keep
their separate ownership and decisions even when co-located. Reference authoritative
template/design revisions; engagement-specific adaptations remain in the engagement.
Link the existing designated progress/checkpoint where relevant; create no second
instance tracker. These areas do not change logical roles or selection-record meanings.

For every starter section distinguish prepared, saved/readback, owner-adopted,
curator-accepted and human-released content as applicable. A seed template provides
none of those decisions. Human notes and dissent retain their author/audience and
remain outside wider contributions unless deliberately permitted.

## Five logical information areas

The initial information architecture groups work by **Marketing, Sales, Delivery,
Standards and Persönlich (Personal)**. These are logical purposes, alongside the
existing Personal/Shared storage categories and business entity types. They do not
require exactly five ChatGPT Spaces, replace suitable existing sites or make Source,
Claim or Result belong to a fixed area. Use the smallest useful sections and
references in authorized homes; one area can span several resources. Co-location
is appropriate only when purpose, audience, policy and operations fit. A label or
hierarchy establishes no access isolation.

| Area and purpose | Content types | Accountable roles and authoritative home | References and audience boundary |
| --- | --- | --- | --- |
| Marketing: explain the firm and its offer to intended audiences | Brand assets, positioning, approved public offering descriptions, public content drafts and released versions, approved references/case material with use permissions | Firm brand/knowledge owner owns brand and reusable public material; offering owner owns offering meaning; authorized person approves/releases the exact outgoing version. Use the designated firm home for those records | Reference authoritative Offering, proof and adopted design/template revisions. Public intent does not make drafts or evidence public; only approved exact material for its permitted audience/purpose leaves the home. This area adds no marketing automation or lead-generation capability |
| Sales: understand buyers and pursue feasible work | Lead/need notes, Account/Relationship and Stakeholder references, Buyer Brief, Opportunity when evidenced, Proposal versions, commercial assumptions/decisions, agreement/order references and Follow-ups | Relationship/pursuit owner owns buyer/pursuit records and next actions; commercial approver owns price/terms/risk decisions. Use the designated restricted relationship/pursuit home; existing owning commercial systems retain their facts | Reference central proof/templates and exact submitted offers. Restrict negotiation/buyer knowledge to agreed participants; an order reference grants neither wider disclosure nor delivery authority by itself |
| Delivery: fulfil each authorized engagement's promise | Work basis and handoff references, Engagement/Baseline, plans/work/milestones, permitted inputs/evidence, analysis/results, adaptations, deliverables/artifacts, status/change/review/release/acceptance records, reservations and closure | Engagement lead is accountable; sponsor, information owner, reviewer and accepting authority retain their separate decisions. Default: a dedicated Shared home per engagement, reusing a compatible existing home | Reference exact pursuit originals and effective central methods/forms. Confidential client/project material and engagement-specific adaptations stay within that engagement's authorized boundary. Central references give neither audience access to the other's content |
| Standards: keep approved shared ways of working usable | Adopted methods/frameworks, output forms, authoritative templates, language/design/quality rules, applicability guidance, effective revisions and adoption decisions | Firm knowledge/method/design owners govern their respective approvals and applicability. Use their designated shared configuration/reference home; canonical common method source retains its existing product-repository authority | Reference brand assets and source methods at their authoritative homes. Candidate, adopted and applied remain distinct. Do not copy authoritative templates across areas; permitted engagement adaptations stay with the engagement until separately approved for shared use |
| Persönlich (Personal): develop a person's work privately | Personal notes, preferences/index references, unfinished research and unshared drafts | The person/author owns the designated Personal home and chooses what to retain or contribute | No automatic promotion to Shared. The roles are accountability descriptions, not appointments of actual people. One
person may hold several roles. Accepted shared knowledge belongs in the appropriate
authorized home for its purpose; placement in Standards alone makes it neither an
approved method nor accepted knowledge. Each fact keeps one current authoritative
home. Area views and working copies identify exact source revisions, coverage and
omissions; they do not move facts or expose restricted linked content by implication.

Apply the existing [record discipline](entity-lineage.md#references-and-skill-handoffs)

## Resolve and provision the exact physical home

Use the existing [binding contract](../workspace-bindings/contract.md) and
[permission and adoption requirements](requirements.md#permissions-and-adoption):

1. Inspect the known entity home and relevant owner catalog; reconcile prior creation
   attempts by actual identity/content before retry. Reuse an existing compatible
   mapping without duplicate setup; an unread current home is not evidence of absence.
2. Record logical roles/entities, actual provider/resource identity and revision,
   Personal or particular Shared context, owner/updater, audience, purpose, current
   authority, retention/continuity/exit terms and selected initial-content references.
   Map SharePoint/OneDrive, Space, another observed supported home or a manual file
   only after inspection. Names, folder structure and URLs establish no capability.
3. Record the actual surface and effective principal, access breadth, enforceable
   controls versus instructional limits, and each needed create/read/edit/readback
   operation. Keep catalog availability, connection, configured action selection,
   runtime exposure and operation evidence separate. A connected app with no exposed
   actions cannot provision a home in that runtime; inspect selection and follow the
   [current configuration and adoption requirements](requirements.md#permissions-and-adoption)
   under specific approval before concluding that the capability is unavailable.
   Observe saved/active identity, confirmations and fresh-runtime tests; a
   configuration description supplies no operation proof. Skill root/child-resource reads
   remain a separate execution-surface prerequisite even after an app read succeeds.
4. Present the concrete minimum create/content/access proposal and obtain applicable
   owner/admin/user confirmation before each required effect. Reuse valid specific
   grants; do not duplicate approvals or infer a grant from setup conversation, a template, work
   authorization or parent connectors. No blanket workspace audience is assumed.
5. Through the supported authorized route, perform only the agreed provisioning and
   initial-content writes, then inspect identity, content/revision, audience/access
   and readback. Record partial/uncertain effects and gaps; configure the resulting
   binding only under its applicable authority. A proposed or created home alone
   passes no retention, continuity or ordinary-workflow gate.

## Authoritative records and temporary local work

Maintain one current authoritative home per fact and label views/copies with exact
source revision, coverage and omissions. A shared home is authoritative only for the
records assigned to it; an extracted commercial reference does not replace its owning
system. Link to existing facts rather than duplicate them on project startup.

Temporary local files may support authorized preparation, rendering or inspection.
Label them as staging/working copies and link their exact inputs/outputs and changes
to the authoritative revisions. Record permitted handling and eventual disposition;
“temporary” establishes no automatic deletion or ephemeral-retention guarantee.
A successful local save establishes no shared audience, durable remote retention or
later-session recovery. Returning or promoting a file to an authoritative home needs
its own permitted save/readback and relevant lineage/navigation checks.

An explicitly owner-designated retained file can serve the existing manual checkpoint
route. Observe save/read and later resupply before claiming that continuity; local
versus remote location alone does not determine authority. Preserve the current
record rather than create a second tracker when shared storage is unavailable.

## Transition, closure and retention handoff

At pursuit-to-delivery transition, reference exact permitted originals and handoff
versions. Reuse the home only when its revised purpose/audience/access and client
terms are authorized. Copying or relocating material needs its own outgoing-use and
storage authority; relocation preserves business identity and verifies new locators
and affected reader links. Private negotiation notes do not migrate by default.

At closure, suspension, cancellation or exit, record the attributable business event,
remaining obligations/reservations, current home, successor/continuity owner and next
actions. Ending work authorization does not authorize deletion or prevent separately
permitted cleanup. Keep issued versions, human notes/dissent and dependency lineage.
Client work remains in its agreed home under the applicable terms.

Propose retention, supported archive/export/restore, managed-copy handling and access
handoff/removal under the actual policy, with owners, dates/unknowns, approvals and
verification. Perform only separately authorized supported effects; record omissions
and inspect uncertain effects before retry. Archive is a storage disposition, not
proof of business closure, deletion, revoked access or permission for firm reuse.
Do not automatically archive, delete, move content, broaden access or revoke grants.
Firm learning/proof is a separately permissioned exact contribution; client acceptance
does not authorize exporting the dossier. Preserve the complete outgoing-use checks
and limitations in the [reuse/exit contract](storage-lifecycle.md#reuse-revocation-and-exit).

For the selected normal workflow, verify reuse without duplication or approved
create/readback, required initial-content reads, preserved original references,
intended-user operations and reader access, fresh-session checkpoint recovery and
the applicable handover/retention disposition. Record source/self-check, operation,
independent review and human acceptance separately. Keep source inspection, actual operation, intended-reader access, continuity, independent review and human acceptance separately evidenced.

## Reuse, revocation and exit

Select proof by relevance, then separate the firm's method, client results, a
person's CV and third-party licensed evidence. Check each owner's current permission
for named, anonymized or reference-call use. Anonymization alone creates no right.
Permission may be evidenced by a standing grant or an attributable owner's/partner's
statement allowed by governing policy; unknown permission remains flagged. Refused,
revoked or expired permission prevents that use.

Before client learning enters the firm home, the owner reviews the **complete**
outgoing material: text, names, links, metadata, comments, attachments and receipts,
with omissions and allowed audience/purpose. A permission on a short lesson does not
authorize a whole engagement dossier. Hidden or uninspectable surfaces prevent a
claim that the complete export was checked. Include no unrelated project inventory.

On revocation stop future managed use, remove managed working copies as policy
requires, identify affected drafts within the authorized scope and assign a human
disposition. Do not promise erasure of released copies or recipients' knowledge.
At exit retain client work in the agreed home, settle administration/continuity,
departed access, retention/export/deletion, open reservations and managed copies.
Recovery must preserve human notes, content lineage and resolvable references in
an authorized destination; report omissions and changed locators. Copying an identifier
alone does not preserve its meaning or access.
