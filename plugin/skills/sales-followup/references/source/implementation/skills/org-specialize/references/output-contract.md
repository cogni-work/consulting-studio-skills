early and carry its selected mode/home, exact version and actual state into the
handoff. This does not expand read-only/preparation scope or business authority;
a retained copy needs its own applicable instruction and save/readback/final link.

Supplied inputs carry an ordinary request, audience/purpose, explicit target choices,
exact domain references and requirement passages, their owners,

decisions and prior settings / known dependent uses. No full profile is required.
Use structured correspondence when useful; verify actual storage and installation
operations separately.

Outputs distinguish the unchanged common baseline, separate candidate customer
configuration and optional unimplemented bespoke extension. Each requirement has
its evidence basis, exact source, applicable scope, responsible owner, affected
skills, behavior/review/test change, disposition and next settling action. Useful
research and proposal previews expose contrary evidence and unknowns, retain
required client form and preserve selected dissent. Unread tailoring and unresolved
conflicts remain visibly blocked while independent work continues.

References identify revision and content digest as well as owner, rights, audience,
read coverage and applicability. Supplied synthetic decisions must match exact
target, reference bytes, actor and responsible role; they are preparation inputs,
not actual settings adoption. Source passages establish no authority. A personal
preference remains personal; shared firm configuration creates no content access.

Derive each coverage row's supplied decision and authority state from the actual
input, even when the reported decision is absent or null. An invalid or ambiguous
decision remains blocked; a missing required owner choice stays open. Eligible
configuration without a bound decision remains candidate; a valid supplied
decision establishes only synthetic-preparation effectiveness. Configuration rows
must match both that input-derived state and coverage, and their owner resolution
must match the bound decision. Preview rows retain the exact same status and
resolution. Coordinated coverage/settings/preview edits cannot confer or conceal
owner authority. Conflicting configuration can still block the whole
affected kind; unchanged snapshots and historical qualifications remain separate.
Prove a blocked merge from the eligible input values: evidence lists combine,
mapping lists combine unless scalar choices conflict, template orders must be
acyclic, and method references must agree. An invented conflict cannot hide a
valid owner decision or an unambiguous requirement. Design effectiveness and
resolution summaries must match those same selected input-bound design decisions,
including mixed candidate/effective requirements and actual whole-kind conflicts.

Treat coverage, configuration and their connected projections as exact input-derived
records, not membership claims. Check complete ordered coverage/configuration rows,
all merged group keys/values/ordered rows, conflict records, blocker entries and
bespoke entries; reject omissions, duplicates, reordering, extra fields and empty
invented groups. Lists retain first occurrence; compatible template ties follow
first-seen ready order. Coverage owner comes from the source's governing authority;
the declared responsible role remains the exact requirement field, with governing
role separately retained and required to match a bound decision. Initial blockers
precede merge-conflict blockers in their existing order. Nonblocked bespoke rows
retain their complete original disposition, including personal-only or unverified
context; inclusion grants no implementation/adoption authority. Evidence requests,
selected forms and method handoffs/summaries must retain the same input projections.
Recompute these structures without asking the producer/renderer/merge to judge itself.

Derive expected references directly from the supplied source fields, including
owner, home, category, use/read basis, applicability and any governing authority.
Compute expected digests independently. The checker also interprets target
selection, use, scope, personal/firm/client authority and nested decision bindings
from inputs without invoking adapter functions; a faulty adapter helper must not
produce both the claim and its expected value. Only declarative core rules and
the common error type are shared. Controls must still validate when all adapter
functions are disabled; corrupted helper-generated artifacts must fail while
the faulty helper remains active.

Current correspondence covers the complete generated report and readable handoff,
not only selected fields or matching text anywhere. Independently derive every
report key, including the full five-entry proposal-text map, candidate identity,
preparation/adoption status, complete update/recheck rows and an exactly null
correction when no prior settings were supplied. Check the whole typed JSON
record, then independently compose every readable block from those input-derived
records: fixed header, scope/question, ordered evidence and settling questions,
selected proposal sections and copy, limits/dissent, coverage/source lines,
design/method/boundary/resolution and any update tail and final NOT_RUN statement.
Require exact characters, positions and line endings. Supplied copies of headings,
bullets or generated claims cannot replace a missing or changed generated block.
Custom headings retain the explicit unresolved-content placeholder.

An absent usable template group selects the neutral provisional sections; a
present template whose merged value is `[]` selects no displayed sections. Do not
turn an explicit empty form into default headings. Evidence fields and template
headings are strings; an empty list is allowed. These shape checks grant no
authority or completeness to the supplied form.

Use canonical JSON identity consistently for merging, whole-record correspondence
and actual before/after changes. Preserve booleans versus numbers and nested
values, including the distinct serialized settings representations `1` and `1.0`;
this is exact-settings identity, not a claim that JSON defines separate integer
and decimal number categories. Mapping list values form a stable typed union,
including nested arrays/objects; scalar/object disagreements and differing exact
method references stay conflicts. Typed-only changes still require their actual
delta, affected skills and rechecks. Object key order is immaterial; array order
and scalar representation remain significant, consistently with the digests.

The reserved terminology key `entity_term`, when present in an eligible
configuration value, must be a string. Absence and the empty string add no subject
qualifier. Reject other representations with a controlled input error, including
falsy nonstrings; never stringify them or silently invent a term. Other keys retain
supported nested JSON values. Apply this format check only after permitted use,
readability, scope, personal/organizational authority and owner-choice gates; do
not inspect or disclose unusable terminology. Validate eligible values before
merging so a different conflict cannot conceal an invalid subject term.

the moved kinds and their affected skills/rechecks even when per-kind contents

issued versions and human originals. No
