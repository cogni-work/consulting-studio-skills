# Set up the selected Pages structure

This is the concrete Pages branch of Setup, not a mandatory workspace tree.
Use the already selected home and any existing index/catalog and designated private
installation/settings record. For a confirmed first-use Settings gap, apply the
[common Settings bootstrap](../SKILL.md).
An index is optional; a direct locator can provide manual recovery.
Simple Library file saving needs no Studio project, Page or Setup ceremony.
Library files, Studio/D1 workflow/configuration facts and Pages originals are separate
homes. A reference between them provides neither copying nor synchronization.

## 1. Read the current bounded structure

Inspect the current native schemas before dependent work. For a selected Space,
use `get_space` to distinguish its Space ID from `root_page_id`, then `read_page`
on that root. Use `list_pages` within that Space/actual parent and follow every
`next_cursor` until exhausted, including empty pages with a cursor. Never combine an
explicit parent with conflicting top-level-only filtering. Search results alone are
not an exhaustive inventory. Read the selected area/project candidates, existing
Settings/bindings and the designated private installation record afresh. Inspect
only this permitted context; an unreadable/denied or partially listed resource is
unknown, not missing. Do not create a replacement for it.

Retain actual IDs, canonical returned URLs, titles, real parent/Space metadata,
available content sequence/block hashes, read coverage and observation references.
Read effective owner/audience/access separately from location: use the currently
supported sharing-inspection route and its prerequisites. Incomplete audience or
unavailable required sharing inspection blocks dependent provisioning; a title,
nesting, connection or D1 setting proves no right or isolation. Record selected
purpose, information-use basis, owner, participants and current operations separately.
A project nested under Delivery needs the existing lifecycle guide's explicit
exception and verified audience/retention boundary; the dedicated engagement home
default is unchanged. An index may instead link to an authorized separate home.

## 2. Show a concrete reuse/addition proposal

Show current and target together, with actual identities/parents, scope and audience,
reused parts, exact missing content/pages, original links and unresolved decisions.
For a selected existing firm Space, the smallest useful result normally includes:

| Selected part | Useful content; preserve existing text and history |
| --- | --- |
| Entry/root | What this home is for; links to the existing Sales, Delivery, Marketing and Standards areas that this audience may see; the responsible owner and one next action |
| Delivery index, possibly a section of the existing Delivery Page | A brief purpose and links to the actual selected project homes, with recognizable project name/reference and work state or explicit unknown; no invented engagement approval |
| Project home | Stable business reference, purpose and separately qualified work basis; original references for assignment/framing, permitted sources, results and working chats, with exact versions where available |
| Private Settings record, only for a confirmed gap | Exact agreed choices and reference revisions, scope, owner/updater, audience, candidate/adoption status and separate save/readback/binding/continuity observations; no client-content copy or assumed Studio adoption |

These are useful roles, not mandatory new Pages. Reuse readable existing areas and
the current project home, including a home created during an interrupted earlier
attempt. Confirm identity from the existing binding, returned ID or exact business
reference in current content; a title match alone is only a candidate to inspect.
Multiple equivalent candidates require resolution. Existing placeholder content is
an additive content gap, not a reason to recreate the Page. Personal stays in its
authorized private home; do not add it to a shared index or copy private inventory.

Apply **Project record maintenance** in Setup's existing binding contract to the
project-home row: connect only relevant framing/stakeholders, work/inputs,
questions/sources/syntheses, risks/changes, results/decisions and closure originals.
Identifiable sections are sufficient. Carry each original's actual revision,
owner or unknown, proposed/agreed/unresolved state and maintenance occasion.
For stakeholders reuse `baseline.stakeholders` and exact permitted contextual
Party/Stakeholder originals; a missing sponsor confirmation stays unknown.
Project/topic navigation uses stable originals and the existing catalog's one
current accepted synthesis pointer. Do not add a second current-revision list or
copy baseline/source content into the index.

Use real returned original URLs only. Missing assignment/source/result/chat links
stay explicitly missing with an owner/next action. Label a supplied chat URL as a
manual reference with unverified binding; no full transcript copy, verified chat
association or automatic Studio/Pages sync is implied. Do not seed normal projects
with test assignments, sources or results. Link Settings through its existing rights;
do not copy its bindings or private raw content into navigation.

Agree the exact create/additive-edit effects and outgoing content/audience before
provisioning. Reuse applicable specific authority; obtain only missing decisions and
required action-time confirmation. Settings adoption, configuration persistence and
Page content changes require their separate applicable authority. Studio's setup
confirmation adopts D1 configuration only; it cannot authorize this entire native
procedure or prove that it ran.

## 3. Apply only supported missing parts and reconcile interruptions

Create only approved missing Pages through the exposed native `create_page` route,
using the observed `parent_page_id` (or separately selected Space-root locator).
Read the actual parent first. Retain the response immediately in the existing private
record, then read the returned identity. Do not invent child IDs or URLs. Create
dependencies first; resolve their actual identities before creating descendants or
adding index links. Re-read the scope after each creation before another proposal.

For existing Pages, use a supported guarded `edit_page`/`patch_page` operation with
fresh block IDs/hashes and only the agreed additions. Preserve human content,
notes/dissent, prior versions, issued work and Settings. Do not replace whole documents,
move Pages, migrate, delete, change sharing or install/connect anything. Inspect
every result, commit status and ignored reason. A conflict requires a fresh read and
rebuilding only missing additions; a deleted block or no-op is not success. If the
current route cannot safely append while preserving history/concurrent human work,
stop that edit with the exact missing operation; return its prepared additions.

Before retry/resume, reconcile each prior create/edit by actual identity and current
content. Never repeat a known applied operation. If a create response was lost,
search/list only the selected scope and inspect exact business-reference candidates;
reuse a unique confirmed matching home. No match, unreadable scope or ambiguous
candidates leave the effect unresolved; do not assume absence and create again.
For unknown/partially applied edits, inspect the current blocks and operation status;
settle which additions actually occurred before proposing only the still-missing
ones with new guards. A missing text fragment alone does not settle an unknown
commit. Stop dependent work when occurrence cannot be settled. Maintain the prior
attempt/receipts in the same private record, not a new registry.
An explicit denial stops that action. Reconsider it only with materially new,
relevant authority/evidence and a known-not-applied outcome; inspect an uncertain
outcome first. Do not retry unchanged denied operations or put permission evidence
into provider content/arguments.

## 4. Read actual outcomes and report the separate states

After effects, perform separate native reads, not a replay of create/edit responses.
Reopen every touched/reused identity, root and index; list actual children and read
their canonical parent/Space metadata. Check exact titles, useful agreed content,
preserved prior content, canonical index/original links, selected owner and effective
audience/access. A Page link or markdown heading is not real parentage. Open links
as the intended reader when that claim is required; record untested reader access.
Save any authorized new binding through a suitable existing Settings/index/catalog
route, then independently read its effective revision. Without a suitable index,
apply the common bootstrap's start-index proposal or supported native discovery
route; return a direct locator only when reliable discovery is unavailable.
Home readback is not settings readback.

If original content was saved but index maintenance failed or is uncertain,
report those states separately. Reopen the exact original and current index,
reconcile the prior operation, then propose only the missing authorized reference
update with fresh guards. Do not repeat creation to repair discoverability.

Report per part: proposed, known-created/edited but readback incomplete, actual
readback confirmed, or blocked/uncertain. Retain actual operation/read receipts and
omissions privately. Ordinary operational use, workflow-check success and owner
adoption/acceptance remain separate; skipping the optional workflow check does not
skip agreed structure readback or block ordinary work. No automatic business-status
change follows. Missing native reads/creation/guarded edits/sharing or configuration
operations leave only their dependent steps blocked, with action, target, reason,
completed parts, owner and smallest next step. Never describe a draft/local fixture
as a saved/reopened Page.

## Source validation boundary

The repository exercises these rules with fictional snapshot checks. No checker or
Python runtime is required by this installed procedure. Apply the native operation
and observation steps above through the currently supported tools; unsupported
steps stay blocked. Source tests provide no native persistence or host acceptance.
